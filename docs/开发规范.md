# GearLink 开发规范

> 本文档定义 GearLink 项目的开发流程、代码规范与公共 API 设计原则。
> 所有贡献者（含维护者）在提交代码前须阅读并遵守。

## 1. 项目结构

```
GearLink/
├── gearlink/               # 包源码
│   ├── __init__.py         # 公共 API 唯一出口（__all__ 显式导出）
│   ├── exceptions.py       # GearLinkError 统一异常层次
│   ├── core/               # 核心抽象：Agent / Memory / Tool 引擎 + 事件体系
│   │   ├── agent.py        # Agent 抽象 + ReactAgent / PlanExecuteAgent
│   │   ├── orchestrator.py # Orchestrator 多 Agent 协作编排层
│   │   ├── memory.py       # Memory / ShortTerm / LongTerm / MemoryManager / VectorStore / ContextBuilder
│   │   ├── events.py       # AgentEvent 事件体系 + JSONL 落盘/回放
│   │   └── tool.py         # ToolRegistry + 工具注册表 + schema + 调度器
│   ├── providers/          # 模型提供者实现（每个服务一个文件）
│   ├── skills/             # 技能扩展（Skill / SkillRegistry / SkillLoader）
│   ├── tools/              # 工具扩展（builtin.py 内置工具、load_skill.py 技能调度入口）
│   ├── mcp/                # McpClient：外部 MCP 服务器工具接入（依赖可选）
│   └── utils/              # 通用工具函数（logging / token_count / usage）
├── tests/                  # 测试代码，目录结构与 gearlink/ 镜像对应
├── docs/                   # 文档
├── examples/               # 可运行的使用示例（每个公共 API 分类至少一个）
├── .github/workflows/      # CI：格式化检查 + lint + 测试 + 覆盖率门禁 + gitleaks
├── pyproject.toml          # 打包与工具链配置（单一事实来源）
├── requirements.txt        # 依赖清单（与 pyproject.toml 保持一致）
├── .env.example            # 环境变量示例（.env 已被 .gitignore 排除）
├── LICENSE                 # MIT
├── README.md               # 项目简介、安装、快速开始、示例链接
├── CONTRIBUTING.md         # 贡献指南（指向本文档）
├── CHANGELOG.md            # 更新日志（Keep a Changelog 格式）
└── TODO.md                 # 待办清单
```

规则：

- 每个 Python 目录必须包含 `__init__.py`，显式导出该目录的公共 API。
- `core/` 不得依赖 `providers/`、`skills/`、`tools/`、`mcp/` 中的具体实现，只能依赖抽象（依赖倒置）。`skills/` 中的 `Skill` / `SkillRegistry` 等契约类型与 `providers/base.py` 同属抽象，`core/` 可以依赖。
- 禁止在源码中使用 `sys.path` 修改技巧解决导入问题；一律使用包内相对导入或完整包路径导入（如 `from gearlink.providers.base import ModelProvider`）。
- 可选依赖（`anthropic` / `mcp`）须懒加载，缺失时核心包仍可正常导入与使用。

## 2. 代码风格

| 项 | 约定 |
|---|---|
| 格式化工具 | `ruff format`，行宽 100 |
| 静态检查 | `ruff check`，配置写在 `pyproject.toml` |
| 类型标注 | 所有公共函数/方法必须有完整的参数与返回值类型标注 |
| Python 版本 | >= 3.10，允许使用现代语法（dataclass、`X \| None` 等） |
| 导入顺序 | 标准库 → 第三方库 → 本项目，各组之间空一行 |
| 日志 | 统一使用标准库 `logging`，模块级日志器为 `logging.getLogger(__name__)`（命名空间以 `gearlink` 为根）；输出策略交给 `enable_logging` / `disable_logging` 全局开关或应用层根日志器，内部模块不得自行添加 handler 或调用 `basicConfig` |

提交前必须通过：

```bash
ruff format .
ruff check .
pytest
```

## 3. 命名规范

- 模块/文件名：小写下划线，如 `openai_provider.py`。**文件名不得与常用第三方库同名**（如禁止命名为 `openai.py`、`memory.py` 等会在顶层导入时产生遮蔽的名称）。
- 类：大驼峰，抽象基类不加 `Base` 前缀，以职责命名（如 `ModelProvider`、`Memory`）。
- 函数/变量：小写下划线，动词开头表示动作（`add_message`、`call_tool`）。
- 常量：全大写下划线（`MAX_ITERATIONS`）。
- 抽象方法的实现应保持同名（如基类定义 `add_message`，子类不得改名为 `add`）。
- 工厂/构造函数注入依赖：`ReactAgent(provider=...)`、`MemoryManager(short_term=..., long_term=...)`，参数名与抽象类型对应。
- 获取类方法用 `get_*`（可返回 None 用 `get_*_or_none` 或文档说明），动作类用动词（`run`、`call_tool`、`add_message`）。
- 布尔参数数量 ≥ 2 个时改为枚举或拆分方法，避免 `f(True, False)` 式调用。
- 公共函数禁止使用 `*args` / `**kwargs` 透传（装饰器等特殊场景除外并说明）。

## 4. 文档字符串

所有公共类、函数必须有 docstring，采用 Google 风格：

```python
def add_message(self, message: dict[str, Any]) -> None:
    """添加一条消息到短期记忆。

    Args:
        message: OpenAI 消息格式字典，须包含 role 与 content 字段。

    Raises:
        ValueError: 当 message 缺少 role 字段时抛出。
    """
```

私有方法（单下划线前缀）可选 docstring，但复杂逻辑必须注释说明意图。

## 5. API 设计原则

### 5.1 总体原则

1. **依赖倒置**：`core/` 只面向抽象编程。Agent 依赖 `ModelProvider` 接口而非具体 SDK；上层通过构造函数注入实现。
2. **单一抽象入口**：每类扩展点只暴露一个抽象基类（如模型调用只有 `ModelProvider.chat`），实现者只需覆盖最少的方法。
3. **统一数据结构**：跨模块传递的数据一律使用本项目定义的 dataclass（如 `ModelResponse`、`ToolCall`），**不得让第三方 SDK 的类型穿透到公共 API 边界之外**。
4. **显式优于隐式**：公共 API 不使用魔法方法、不做隐式全局状态注册；配置通过构造参数传入。
5. **最小公开面**：只有从 `__init__.py` 显式导出的名称才是公共 API；下划线前缀、未导出的一律视为内部实现，允许随时变更。

### 5.2 抽象接口定义

以 `ModelProvider` 为模板，所有抽象接口须满足：

- 继承 `ABC` 并用 `@abstractmethod` 标注；docstring 必须写明契约（输入约束、返回保证、异常情况）。
- 参数尽量给出合理默认值，使最简实现只需必填最少参数。
- 接口一旦发布即冻结签名；确需变更时走 §10 废弃流程。

### 5.3 数据结构规范

- 跨模块数据载体一律用 `dataclass`（必要时 `frozen=True`），字段全部带类型标注。
- 字段命名与业界通行格式对齐：工具调用沿用 `id / name / arguments`，消息沿用 `role / content / tool_calls / tool_call_id`。
- 需要序列化的结构（写入记忆、持久化）须提供 `to_dict()` / `from_dict()` 方法对，且保证往返一致。
- 不得用裸 `dict` 承载本项目自创概念（如工具调用结果）；OpenAI 消息格式等既有标准除外。

## 6. 扩展点契约

GearLink 有四类扩展点，均遵循「注册表 + schema + 调度器」三件套模式（参考 `core/tool.py`）：

| 扩展点 | 位置 | 契约 |
|---|---|---|
| Provider | `providers/` | 继承 `ModelProvider`，实现 `chat` |
| Tool | `tools/` | 普通函数 + JSON Schema 描述，注册进 `ToolRegistry`（或模块级默认注册表） |
| Skill | `skills/` | 每个技能一个目录含 `SKILL.md`（YAML frontmatter 含 name / description）；`SkillRegistry` 显式登记，`ReactAgent(skill_registry=...)` 注入；L2 指令经 `load_skill` 工具按需加载（见 `架构设计.md` §6.3） |
| Memory | `core/memory.py` | 继承 `Memory`，实现 `add_message` / `get_messages` / `clear`；需要检索注入时覆写 `build_context` 或实现 `ContextBuilder` 协议 |

通用规则：

- **注册表显式声明**：`ToolRegistry` 实例化注入或模块级默认注册表，key 为唯一名称，禁止运行时隐式扫描。
- **schema 与实现同源**：工具的 JSON Schema 必须与函数签名严格一致，新增/修改工具时两者同步更新。
- **调度器集中错误处理**：调用方（如 `ToolRegistry.call_tool`）负责未知名称、参数解析、执行异常的统一兜底，实现函数本身无需防御性包装。
- 第三方贡献的扩展不得修改 `core/`，只能新增文件并注册。

补充说明：

- `MemoryManager` 是面向「短期 + 长期」场景的内置组合器，不是 `Memory` 子类——它提供 `build_context` / `end_session` 等专用接口（见 `架构设计.md` §7）。自定义组合逻辑时可参考其实现，也可直接组合任意 `Memory` 实现。
- `ToolRegistry` 支持实例化注入 `ReactAgent(tool_registry=...)`，使同一进程内多个 Agent 持有隔离的工具集与技能集；未注入时使用模块级默认注册表（向后兼容）。工具执行期间经 `contextvars` 暴露当前注册表，供 `load_skill` 等工具解析所属 Agent 的技能注册表。
- 所有新增构造参数均为可选，默认值等价现状，向后兼容。

## 7. 错误处理规范

建立统一异常层次，于 `gearlink/exceptions.py` 集中定义（与代码实际继承关系严格对齐）：

```
GearLinkError            # 所有项目异常的基类
├── ProviderError        # 模型服务调用失败（retryable 标记瞬时故障，供 max_retries 决策）
├── ToolError            # 工具注册/执行失败
│   └── ToolNotFoundError
├── MemoryError          # 记忆读写失败
└── SkillError           # 技能相关失败
    ├── SkillNotFoundError      # 按名查找技能未命中
    ├── SkillLoadError          # SKILL.md 解析失败
    ├── SkillValidationError    # 元数据（YAML frontmatter）校验失败
    └── SkillExecutionError     # 执行技能辅助脚本时出错
```

规则：

- 公共 API 只抛出 `GearLinkError` 体系的异常；捕获第三方异常后须转换包装，保留 `__cause__`。
- 工具执行失败在 ReAct 循环内属于**可恢复信号**：以文本结果写回消息交给模型处理，不得直接中断。
- 异常消息面向开发者，包含足够定位信息（工具名、模型名等），不泄露密钥。

## 8. 配置与密钥管理

- **严禁在源码中硬编码 API key、密码、令牌等敏感信息。**
- 敏感配置一律从环境变量读取，本地开发使用 `.env` 文件（已被 `.gitignore` 排除）：

```python
import os

api_key = os.environ["DEEPSEEK_API_KEY"]  # 缺失时应抛出带提示的明确错误
```

- 默认值（如 base_url、模型名）可以作为常量定义，但密钥不行。

## 9. 测试规范

- 使用 `pytest`，测试文件位于 `tests/`，命名为 `test_<模块名>.py`。
- 测试函数命名：`test_<被测行为>_<场景>`，如 `test_short_term_memory_truncates_over_limit`。
- **涉及外部服务的调用（模型 API、网络）必须 mock**，CI 中不允许真实调用。
- 核心模块（`core/`）要求测试覆盖率 ≥ 80%。
- 每个公共 API 须在 `examples/` 中至少有一个可直接运行的示例，在 `tests/` 中覆盖正常路径与至少一个异常路径。三者缺其一，PR 不予合入。

## 10. 兼容性与废弃流程

- 遵循语义化版本：破坏性公共 API 变更只能在 MAJOR 版本发布。
- 废弃流程（至少跨一个 MINOR 版本）：
  1. 新版本中保留旧接口，标注 `@deprecated` 并发出 `DeprecationWarning`；
  2. docstring 注明替代方案与计划移除版本；
  3. CHANGELOG 的 `Deprecated` 段落记录；
  4. 下一个 MAJOR 版本移除。
- 内部 API（未导出/下划线前缀）不受此约束。

## 11. Git 工作流

### 11.1 分支模型

- `main`：始终可发布，只接受 PR 合入，禁止直接推送。
- `feat/<描述>`、`fix/<描述>`、`docs/<描述>`：功能/修复/文档分支。

### 11.2 提交信息

遵循 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/)：

```
<type>(<scope>): <简述>

[可选正文：说明动机与上下文]
```

type 取值：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`。
示例：`feat(providers): 新增 AnthropicProvider 实现`。

### 11.3 PR 要求

- 一个 PR 只做一件事；提交前自行 rebase 整理历史。
- 必须通过 CI（格式化检查 + lint + 测试）。
- 涉及公共 API 变更的 PR 须同步更新文档与 CHANGELOG。

## 12. 版本与发布

- 遵循 [语义化版本](https://semver.org/lang/zh-CN/) `MAJOR.MINOR.PATCH`。
- 每次发布更新 `CHANGELOG.md`（Keep a Changelog 格式）。
- 版本号唯一来源为 `pyproject.toml` 中的 `[project] version`。

## 13. 开源合规

- 根目录保留 `LICENSE`（已采用 MIT 许可证）。
- `README.md` 须包含：项目简介、安装、快速开始、示例链接、公共 API 一览。
- 提供 `CONTRIBUTING.md` 指向本文档。
- `CHANGELOG.md` 记录所有显著变更（Keep a Changelog 格式，遵循语义化版本）。
- CI 已接入 `gitleaks` 全历史扫描；发布前须确认扫描通过且历史中无泄露密钥，必要时轮换受影响密钥。
- 严禁在代码或提交历史中硬编码 API key 等敏感信息；密钥一律经环境变量读取（见 §8）。
